Looking at both the E22-900T30D datasheet constraints and the ESP32-S3 N16R8 pin reservations before making a recommendation.

  The ESP32-S3 N16R8 has several GPIO ranges to avoid:
  - GPIO6–11: Internal Quad Flash
  - GPIO33–37: Octal Flash/PSRAM (the N16R8 uses both, so these are consumed)
  - GPIO0, 3, 45, 46: Strapping pins — avoid for M0/M1 especially, since their state at boot affects startup behavior

  Suggested assignments:

  ┌───────────────┬───────────────┬───────────┬────────────────────────────────────────────────────┐
  │    E22 Pin    │ ESP32-S3 GPIO │ Direction │                     Rationale                      │
  ├───────────────┼───────────────┼───────────┼────────────────────────────────────────────────────┤
  │ TXD (E22→ESP) │ GPIO18        │ Input     │ UART1 RX                                           │
  ├───────────────┼───────────────┼───────────┼────────────────────────────────────────────────────┤
  │ RXD (ESP→E22) │ GPIO17        │ Output    │ UART1 TX                                           │
  ├───────────────┼───────────────┼───────────┼────────────────────────────────────────────────────┤
  │ AUX           │ GPIO4         │ Input     │ Interrupt-capable; use to detect module busy/ready │
  ├───────────────┼───────────────┼───────────┼────────────────────────────────────────────────────┤
  │ M0            │ GPIO5         │ Output    │ Clear of strapping and flash pins                  │
  ├───────────────┼───────────────┼───────────┼────────────────────────────────────────────────────┤
  │ M1            │ GPIO21        │ Output    │ Clear of strapping and flash pins                  │
  └───────────────┴───────────────┴───────────┴────────────────────────────────────────────────────┘

  A few things worth knowing before wiring:

  Power: At 30 dBm (1 W) the E22-900T30D can draw ~700 mA peak during transmission. Don't power it from the ESP32-S3's onboard 3.3 V regulator — give it a dedicated supply capable
  of the peak current. The logic I/O is 3.3 V compatible so no level shifting is needed.

  AUX behaviour: AUX goes low while the module is busy (transmitting, receiving, changing config). It's worth wiring it to an interrupt-capable pin (all the ones above qualify) so
  you can use gpio_isr_handler rather than polling.

  M0/M1 at boot: Since M0/M1 are outputs driven by the ESP32-S3, they'll float briefly during reset. If the E22 latches mode on power-up before the ESP32 drives them, add 10 kΩ
  pull-downs to default to normal UART mode (M0=0, M1=0) during the boot window.

● The log line comes from the C1 readback in e22_configure() — after the C2 write programs the module, the code immediately reads back all nine registers (addresses 0x00–0x08) to
  confirm they stuck. Here's every field:

  ---
  addr=0000 — ADDH/ADDL (addresses 0x00, 0x01)
  
  The module's own 16-bit address, stored as two bytes: high byte 00, low byte 00 → address 0x0000.

  This is the factory default and it doesn't matter in this configuration. The E22 has two transmission modes:

  - Transparent mode (what we use): every module on the same channel hears every transmission. The ADDH/ADDL registers are completely ignored for routing — the module is a dumb pipe.
  - Fixed-point mode: the sender prefixes each packet with the destination's ADDH+ADDL+CH bytes, and the E22 handles addressing in hardware.

  Since REG6 selects transparent mode (see below), addr=0000 is a don't-care. Both base and rover could have any address and still communicate.

  ---
  net=00 — NETID (address 0x02)

  A secondary grouping byte. All modules that should hear each other must share the same NETID. 0x00 is the factory default. Since both devices come out of the box at net=00, they're
  on the same network without any configuration needed. You'd change this if you had multiple independent LoRa pairs operating on the same channel in the same area and needed to
  prevent cross-talk.

  ---
  reg3=64 — UART baud rate, parity, air data rate (address 0x03)
  
  0x64 = 0b 0110 0100, split into three fields:

  ┌──────┬───────┬──────────────────────────┐
  │ bits │ value │         meaning          │
  ├──────┼───────┼──────────────────────────┤
  │ 7:5  │ 011   │ UART = 9600 baud         │
  ├──────┼───────┼──────────────────────────┤
  │ 4:3  │ 00    │ 8N1 (no parity)          │
  ├──────┼───────┼──────────────────────────┤
  │ 2:0  │ 100   │ Air data rate = 9.6 kbps │
  └──────┴───────┴──────────────────────────┘

  The UART baud rate (9600) is the speed between the ESP32 and the E22 module on the physical UART pins. The air data rate (9.6 kbps) is the over-the-air LoRa symbol rate — a separate
  setting. These happen to be the same number here but are completely independent.

  At 9.6 kbps air rate the E22 uses a relatively fast LoRa spreading factor and bandwidth, trading range for throughput. This is the right balance for RTCM: you need to move ~500–600
  bytes per GNSS epoch (1 Hz), and 9.6 kbps gives you comfortable headroom for bursts of MSM4 frames.

  ---
  reg4=03 — Sub-packet size and TX power (address 0x04)

  ---
  reg4=03 — Sub-packet size and TX power (address 0x04)

  0x03 = 0b 0000 0011, two relevant fields:

  ┌──────┬───────┬─────────────────────────────┐
  │ bits │ value │           meaning           │
  ├──────┼───────┼─────────────────────────────┤
  │ 7:6  │ 00    │ Sub-packet size = 240 bytes │
  ├──────┼───────┼─────────────────────────────┤
  │ 1:0  │ 11    │ TX power register = 3       │
  └──────┴───────┴─────────────────────────────┘

  Sub-packet size (240 bytes): When a message longer than the sub-packet size arrives at the E22 UART, the module automatically splits it and sends it in chunks. 240 bytes is the
  maximum (and what we want) — it minimises the number of LoRa air frames needed per RTCM epoch, keeping latency low. Smaller sub-packets would mean more preamble overhead and higher
  AUX-busy time.

  TX power: The register value 0b11 maps to the lowest power step on the E22-900T22S. The code computes the register using the formula (30 − dbm) / 3, which was written for the T30S
  (30 dBm) variant. For the T22S (22 dBm max) the actual power table is:

  ┌──────────┬───────────────┐
  │ reg bits │ actual output │
  ├──────────┼───────────────┤
  │ 00       │ 22 dBm        │
  ├──────────┼───────────────┤
  │ 01       │ 17 dBm        │
  ├──────────┼───────────────┤
  │ 10       │ 13 dBm        │
  ├──────────┼───────────────┤
  │ 11       │ 10 dBm        │
  └──────────┴───────────────┘

  So the log says "21 dBm" because that's what power_reg(21) computed, but the hardware is actually outputting ~10 dBm. The LoRa link worked perfectly at 0 errors over 400 seconds,
  so 10 dBm is more than adequate at field-test distances. The formula needs correcting if you ever need to control power precisely — for example if you were hitting the FCC Part 15
  limit or trying to conserve battery by running at minimum usable power.

  ---
  chan=52 — Channel (address 0x05)

  The frequency formula for the E22-900T22S is:

  f = 850.125 + channel (MHz)
  chan 52 → 850.125 + 52 = 902.125 MHz

  This puts the link on 902.125 MHz, well inside the US 915 MHz ISM band (902–928 MHz). Channel is shown in decimal in the log (52) because that's most readable, but it's stored as a
  raw byte 0x34. Both devices read back chan=52, confirming they're locked to the same frequency — essential for them to hear each other.

  ---
  reg6=00 — Transmission mode, RSSI byte, LBT (address 0x06)

  0x00 = 0b 0000 0000. The three meaningful bits:

  ┌─────┬───────┬───────────────────────────────────┐
  │ bit │ value │              meaning              │
  ├─────┼───────┼───────────────────────────────────┤
  │ 7   │ 0     │ RSSI byte disabled                │
  ├─────┼───────┼───────────────────────────────────┤
  │ 6   │ 0     │ Transparent mode                  │
  ├─────┼───────┼───────────────────────────────────┤
  │ 5   │ 0     │ LBT (listen-before-talk) disabled │
  └─────┴───────┴───────────────────────────────────┘

  Bit 7 is the dangerous one. When set to 1, the E22 appends a one-byte RSSI value to the end of every received packet before writing it to the UART. That extra byte would land
  inside every RTCM3 frame, corrupting the CRC-24Q check and causing the rover to discard every message. This is why the code explicitly checks rb[9] & 0x80 in the C1 readback and
  logs a warning if it's set — the C2 write should have forced it to 0, but a silent config failure would leave it at whatever the factory default was.

  Bit 6 selects transparent vs. fixed-point routing (see addr above). 0 = transparent, which is what makes both devices broadcast-receive without any address configuration.

  ---
  crypt=0000 — Encryption key (addresses 0x07–0x08)

  A 16-bit AES-like hardware encryption key. 0x0000 = encryption disabled. When non-zero the E22 encrypts every byte before transmitting and decrypts on receive, transparently. Both
  ends must have the same key or every frame is garbage.

  0x0000 is the factory default and is fine here — RTCM corrections aren't sensitive data, and adding encryption would require synchronising keys on both devices without adding any
  meaningful security benefit in a local field setup.

  ---
  Why the readback matters

  The C1 readback happens after the C2 write, not before. If the C2 write silently failed (wrong ACK byte, garbled response, AUX timing issue), the C1 would show factory-default
  values — most critically reg6=0x00 would still be fine but reg3 might differ, and chan might be wrong. Seeing reg3=64 chan=52 reg6=00 exactly matching what was written is the positive confirmation that the config write actually landed. That's why those three checks (channel mismatch, RSSI byte, fixed-point mode) are wired up as explicit warnings.

  Bug #1 — svin_dur_s / svin_acc_m always 0

  Root cause: gnss_poll_svin_status() sends the wrong PQTM command format.

  // gnss_lc29h.c:759 — current, wrong:
  pqtm_send("PQTMSVINSTATUS,R");
  // produces: $PQTMSVINSTATUS,R*XX  (not a valid PQTM query)

  The parser expects a response matching $PQTM,PQTMSVINSTATUS,0,.... The correct query is:

  // fix:
  pqtm_send("PQTM,PQTMSVINSTATUS,R");
  // produces: $PQTM,PQTMSVINSTATUS,R*XX  ← correct PQTM query format

  The svin_valid column works only because broadcast_rtcm() forcibly sets s_last_svin.valid = true when it first sees a 1005 frame — that's a workaround that happens to be
  correct, but dur_s and mean_acc_m never get populated.

  Fix is one character change at gnss_lc29h.c:759.

  Bug #2 — h_acc_m is HDOP×3, not RTK accuracy
  
  PAIR513 (which enables $PQTMEPE output) is returning no-response. The code logs this at boot:
  3,gnss: PAIR513 (EPE enable) ack=no-response

  So s_epe_received stays false and h_acc_m is computed as hdop * 3.0f the entire session. With HDOP ≈ 0.47–0.62 during a good-geometry Fix, this gives 1.4–1.9 m — which is
  what you see in every row, regardless of whether you're at Float or Fixed.

  The position scatter (±2–4 cm during stable Fixed) shows the actual RTK accuracy is centimeter-level, but the CSV column h_acc_m is useless for distinguishing Float from
  Fixed. This needs to be fixed to make the capture quality gate (h_acc ≤ threshold) meaningful.

  The ACK detection pattern in the reader is looking for $PQTM,PAIR513,... — a PAIR-in-PQTM format that doesn't exist. PAIR ACKs use $PAIR001,<ID>,<result> format. This
  needs investigation — either PAIR513 is wrong for the RSA firmware, or the ACK pattern and/or timing is off.
